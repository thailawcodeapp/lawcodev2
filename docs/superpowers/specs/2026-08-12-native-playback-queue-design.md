# ย้ายการเดินคิวเล่นเสียงไปฝั่ง native (Android) — Design

วันที่: 2026-08-12
สถานะ: อนุมัติแล้ว รอเขียนแผนลงมือ
สาขา: `cloud-sync`
บิลด์ที่ใช้เก็บหลักฐาน: 80 (v1.0.6)

---

## 1. ปัญหา

เสียงอ่านหยุดเงียบประมาณ 60–85 วินาทีหลังผู้ใช้ออกจากแอป (กด Home ก็พอ ไม่ต้องปิดจอ) และเล่นต่อเองทันทีเมื่อเปิดแอปกลับมา จุดที่หยุดเป็นเวลาคงที่นับจากออกจากแอป ไม่ได้ขึ้นกับจำนวนย่อหน้าที่เล่นไปแล้ว

บิลด์ 74–79 แก้ไปสี่ครั้งโดยไม่เปลี่ยนจุดที่หยุดเลยแม้แต่ครั้งเดียว

---

## 2. หลักฐาน

เก็บผ่าน `adb` บน Samsung SM-S938B (Android 16, One UI) วันที่ 2026-08-12 ขณะเล่นเสียงและกด Home ออกจากแอป

### 2.1 ระบบไม่ได้แช่แข็งโปรเซส

`dumpsys activity processes` ทุก 5 วินาที ต่อเนื่อง 2 นาที 17 วินาที — ทุกจุดข้อมูล ทั้งโปรเซสแอปและโปรเซส WebView renderer:

```
mHasForegroundServices=true
isFreezeExempt=false isPendingFreeze=false isFrozen=false
Proc # 3: prcp F/S/FGS ... com.lawcodev2.app (fg-service)
```

foreground service ทำงานถูกต้อง โปรเซสอยู่ที่ระดับ perceptible ไม่เคยถูกลดชั้นหรือแช่แข็ง

### 2.2 เครื่องเล่นเสียง native เล่นจบคลิปตามปกติ

`dumpsys audio` ทุก 3 วินาที — เห็น `android.media.MediaPlayer` ของแอปสลับตัวใหม่ทุกย่อหน้า และตัวถัดไปถูกสร้างรอไว้ล่วงหน้าเสมอ:

```
09:38:50 | 108847=started 108855=idle     ← เล่นอยู่ + ตัวถัดไปโหลดรอแล้ว
09:39:02 | 108855=started 108863=idle
09:39:20 | 108855=stopped 108863=idle     ← เงียบ: ตัวที่รออยู่ไม่เคยถูกสั่งเล่น
```

เล่นต่อเนื่อง 82 วินาที (5 คลิป) แล้วหยุด **โดยที่คลิปถัดไปโหลดเสร็จพร้อมเล่นรออยู่แล้ว**

### 2.3 สายขาดตรงรอยต่อกับ JavaScript พอดี

logcat เปรียบเทียบสองจังหวะในเซสชันเดียวกัน:

| | คลิปจบตอนปกติ (09:38:58) | คลิปจบตอนเงียบ (09:39:17) |
|---|---|---|
| `playback complete` | มี | มี |
| `setLooping` / `seekTo` / `setVolume` | มี ภายใน 15 ms | ไม่มี |
| `AudioDispatcher: play` | มี | ไม่มี |
| `MediaPlayer-JNI: start` | มี | ไม่มี |

native รายงาน "เล่นจบแล้ว" ขึ้นไปเรียบร้อยทั้งสองครั้ง ครั้งที่สองไม่มีคำสั่งใดกลับลงมาอีกเลย

### 2.4 heartbeat สองตัวหยุดพร้อมกัน

จากบิลด์ 80: heartbeat ของลูปเล่นเสียง และ `setInterval` อิสระที่ไม่เกี่ยวกับลูปเลย หยุดห่างกัน 1 มิลลิวินาที หลังเดินสม่ำเสมอมา 85 วินาที — เป็นลายเซ็นของ "เอนจิน JavaScript หยุดทำงาน" ไม่ใช่ "ลูปค้างรอ promise"

### 2.5 ปุ่มล็อกสกรีนก็ตายไปด้วย

ยิงคำสั่งเล่นผ่านสาย (`cmd media_session dispatch play`) ขณะเงียบ โดยไม่แตะเครื่องและไม่เปิดแอป — ไม่มีอะไรเกิดขึ้นตลอด 20 วินาที เพราะปุ่มพวกนี้วิ่งผ่าน `setRemoteHandlers` ใน JS ที่ถูกแช่แข็งอยู่ **นี่คือบั๊กที่มีอยู่เดิมแต่ยังไม่เคยถูกรายงาน**

### 2.6 สรุป

เอนจิน JavaScript ใน WebView หยุดทำงานหลังแอปลงแบคกราวด์ประมาณ 60–85 วินาที ขณะที่ทุกอย่างฝั่ง native — โปรเซส, foreground service, เครื่องเล่นเสียง, แม้แต่ไฟล์ของย่อหน้าถัดไป — พร้อมและแข็งแรงตลอด

## 3. สิ่งที่ตัดออกแล้ว พร้อมเหตุผล

| สมมติฐาน | ตัดออกเพราะ |
|---|---|
| Cached Apps Freezer แช่แข็งโปรเซส | §2.1 `isFrozen=false` ทุกจุด |
| foreground service ไม่ได้เริ่มจริง | §2.1 `isForeground=true` ตลอด |
| CPU หลับ (ต้องใช้ wake lock) | §2.1 โปรเซสไม่ถูกระงับ |
| Doze ตัดเน็ต | §2.2 ไฟล์ถัดไปโหลดสำเร็จแล้ว |
| WebView ถูกลดความสำคัญ | §2.1 renderer อยู่ที่ `prcp` ผูกกับ FGS |
| Capacitor เรียก `pauseTimers()` | `MockCordovaWebViewImpl.setPaused()` เป็นผู้เรียกเพียงจุดเดียว และ `keepRunning` เป็น `true` เสมอ เพราะ `android/app/src/main/res/xml/config.xml` ไม่ได้ตั้งค่า `KeepRunning` |
| `audioFocusLoss` ทำให้ลูปค้าง | §2.4 เอนจินหยุด ไม่ใช่ promise ค้าง (แต่การแก้ในบิลด์ 79 เป็นช่องโหว่จริงของปลั๊กอิน จึงคงไว้) |

## 4. เป้าหมายและเกณฑ์รับ

เล่นเสียงต่อเนื่องขณะอยู่แบคกราวด์ได้ไม่จำกัดความยาว โดยไม่ต้องพึ่ง JavaScript

**เกณฑ์รับ:** เล่นต่อเนื่อง 60 นาทีขณะแอปอยู่แบคกราวด์ โดย `dumpsys audio` แสดงเครื่องเล่นสลับตัวใหม่ต่อเนื่องไม่มีช่วงว่าง

**ลายเซ็นที่คาดหวังหลังแก้:** heartbeat ทั้งสองตัวยังหยุดเหมือนเดิม (JS ยังถูกแช่แข็ง) **แต่เสียงเล่นต่อ** — ตรงข้ามกับพฤติกรรมวันนี้ ซึ่งเป็นหลักฐานว่า JavaScript ออกจากเส้นทางวิกฤตแล้วจริง

**ขอบเขต:** Android เท่านั้น เว็บและ iOS ใช้ลูป JavaScript เดิมต่อไปโดยไม่แก้ไข

## 5. สถาปัตยกรรม

### 5.1 วันนี้

```
runLoop (JS) ──ทีละย่อหน้า──> playFile() ──> NativeAudio.preload + play
             <────'complete'────
```

ลูปต้องตื่นทุกครั้งที่ย่อหน้าจบ — คือจุดที่พัง

### 5.2 แบบใหม่

```
playItems() ──คิวที่เหลือทั้งหมด──> NativeAudio.setQueue()
                                    native เดินคิวเอง ไม่ถาม JS อีก
            <──queueAdvance (เมื่อ JS ตื่นอยู่)──
```

### 5.3 อะไรอยู่ที่ไหน

**ย้ายไป Java:** เดินคิว, โหลดไฟล์, ปุ่มล็อกสกรีน (เล่น/หยุด/มาตราถัดไป/ก่อนหน้า), กติกา repeat

**คงไว้ใน JS:** สร้างเพลย์ลิสต์ (`buildSectionItem`, `flatten`), UI, ไฮไลต์ย่อหน้า, จำตำแหน่ง, ตั้งค่าเสียง/ความเร็ว, ปุ่มฟังตัวอย่างใน Settings, และลูป JS เดิมทั้งหมดสำหรับเว็บ/iOS

### 5.4 การโหลดไฟล์ — ไม่ต้องเขียนใหม่

`RemoteAudioAsset.java` ในปลั๊กอินใช้ Media3/ExoPlayer พร้อม `SimpleCache` ขนาด 100 MB แบบ LRU อยู่แล้ว จึงรับ URL จริงไปโหลดและแคชเองได้ทันที ไม่ต้องเพิ่มโค้ดเครือข่ายใดๆ

### 5.5 ที่อยู่ของโค้ด

โค้ด Java เพิ่มใน `@capgo/native-audio` ที่ patch อยู่แล้ว (`patches/@capgo+native-audio+8.4.2.patch`)

**ทางเลือกที่พิจารณาแล้วไม่เอา:** เขียนปลั๊กอินของเราเองใน `android/app/` เพื่อให้ patch เล็กลง — ไม่เอาเพราะจะมีปลั๊กอินสองตัวแย่งกันถือ MediaSession, notification และ audio focus ซึ่งเป็นแหล่งบั๊กที่ร้ายกว่าปัญหาขนาด patch

### 5.6 ต้นทุนที่ยอมรับ

จะมีเครื่องเล่นสองตัวในโค้ดเบส — คิว native (Android) และลูป JS (เว็บ/iOS) แยกเป็นโมดูลใหม่ `src/lib/nativeQueue.js` โดย `playItems()` เลือกทางเดียวตั้งแต่ต้น **ลูปเดิมใน `tts.js` ไม่ถูกแก้** เพื่อไม่ให้เทสต์ 429 ตัวที่ผ่านอยู่แล้วเสี่ยงพัง

## 6. สัญญา API

### 6.1 JS → native

| คำสั่ง | พารามิเตอร์ | เรียกเมื่อ |
|---|---|---|
| `setQueue` | `entries`, `startIndex`, `repeat`, `rate` | กดเล่น / เปลี่ยนเสียง |
| `skipToQueueIndex` | `index` | ปุ่มมาตราถัดไป/ก่อนหน้าในแอป, เลือกมาตราจากรายการ |
| `pauseQueue` | — | กดหยุดชั่วคราว |
| `resumeQueue` | — | กดเล่นต่อ |
| `setQueueRepeat` | `repeat` | เปลี่ยนโหมดวนซ้ำ |
| `setQueueRate` | `rate` | เปลี่ยนความเร็ว |
| `getQueueState` | — | แอปกลับมาเห็นหน้าจอ |
| `clearQueue` | — | กดหยุด |

`setQueue` เริ่มเล่นทันทีจาก `startIndex` — ไม่ต้องสั่งเล่นซ้ำอีกคำสั่ง

`pauseQueue` / `resumeQueue` ทำงานระดับคิว ไม่ใช่ระดับ asset: `resumeQueue` เล่นต่อจากจุดที่ค้างในย่อหน้าเดิม และเมื่อย่อหน้านั้นจบก็เดินคิวต่อตามปกติ ต่างจาก `pause`/`resume` เดิมของปลั๊กอินที่ผูกกับ `assetId` ตัวเดียวและไม่รู้จักคิว

`getQueueState` คืน:

```js
{
  index,        // ตำแหน่งในคิว, -1 เมื่อไม่มีคิว
  itemIndex,    // มาตราที่กำลังเล่น
  paraIndex,    // ย่อหน้าที่กำลังเล่น
  playing,      // กำลังเล่นอยู่จริงไหม
  stalled,      // หยุดเพราะเล่นไม่ได้ (§8.1) ไหม
  error         // เหตุผลที่หยุด, null เมื่อไม่ได้หยุด
}
```

หนึ่งรายการในคิว:

```js
{
  url,          // file:// ถ้ามีในแคชแอปแล้ว ไม่งั้น https:// ตัวจริง
  title,        // "มาตรา 369"
  artist,       // "ทำลายประกาศ… · ย่อหน้า 2/3"
  artworkUrl,   // ปกจาก R2 (ตัวเดียวกันทุกรายการ)
  itemIndex,    // มาตราไหน — ใช้ทำ repeat section และปุ่มข้ามมาตรา
  paraIndex     // ย่อหน้าที่เท่าไรในมาตรานั้น
}
```

`repeat` เป็นค่าใดค่าหนึ่งใน `'off' | 'section' | 'all'` ตรงกับ `REPEAT_MODES` ใน `tts.js`

### 6.2 native → JS

| เหตุการณ์ | ข้อมูล | ความหมาย |
|---|---|---|
| `queueAdvance` | `index`, `itemIndex`, `paraIndex` | ย้ายไปย่อหน้าใหม่ |
| `queueEnded` | — | จบคิว (เฉพาะ `repeat: 'off'`) |
| `queueStalled` | `index`, `itemIndex`, `paraIndex`, `error` | หยุดเพราะเล่นไม่ได้ |

ส่งแบบไม่รับประกันผู้รับ เพราะ JS อาจถูกแช่แข็งอยู่ — ความถูกต้องมาจาก `getQueueState()` ใน §7 ไม่ใช่จากเหตุการณ์เหล่านี้

### 6.3 กติกา repeat ฝั่ง Java

- `off` — เล่นถึงรายการสุดท้ายแล้วจบ ส่ง `queueEnded`
- `all` — จากรายการสุดท้ายวนกลับไปดัชนี 0
- `section` — เมื่อรายการถัดไปมี `itemIndex` ไม่ตรงกับรายการปัจจุบัน ให้กระโดดกลับไปรายการแรกที่มี `itemIndex` เดียวกัน

ทั้งสามโหมดไม่ต้องส่งคิวใหม่ เพราะรายการทั้งชุดยังอยู่ในหน่วยความจำฝั่ง native และไฟล์ที่เคยเล่นแล้วอยู่ในแคช ExoPlayer จึงวนซ้ำได้โดยไม่ใช้เน็ตเพิ่ม

### 6.4 ฟังก์ชันเดิมใน `tts.js` ชี้ไปที่ไหน

API สาธารณะของ `tts.js` ไม่เปลี่ยนเลย — ผู้เรียกทั้งหมด (ปุ่มในแอป, `setRemoteHandlers`) ใช้เหมือนเดิม เปลี่ยนแค่ปลายทางเมื่ออยู่บน Android:

| ฟังก์ชันเดิม | บน Android | บนเว็บ/iOS |
|---|---|---|
| `playItems()` | `setQueue` | `runLoop` เดิม |
| `pause()` | `pauseQueue` | เดิม |
| `resume()` | `resumeQueue` | เดิม |
| `next()` / `prev()` / `goToItem()` | `skipToQueueIndex` | `jumpToItem` เดิม |
| `stop()` | `clearQueue` | `doStop` เดิม |
| `setRepeat()` | `setQueueRepeat` | เดิม |
| `setRate()` | `setQueueRate` | เดิม |

### 6.5 เปลี่ยนเสียงชาย/หญิงกลางคัน

URL ทั้งชุดเปลี่ยน จึงต้องเรียก `setQueue` ใหม่จากตำแหน่งปัจจุบัน การกระทำนี้เกิดใน Settings ขณะแอปเปิดอยู่เสมอ JS จึงยังตื่นและทำได้ทันที (สอดคล้องกับ `rebuildItemForVoice` ที่มีอยู่เดิม)

## 7. การ sync สถานะกลับ

หลักการ: **JS ไม่เชื่อสถานะของตัวเองอีกต่อไปเมื่อกลับมาจากแบคกราวด์**

เมื่อแอปกลับมาเห็นหน้าจอ (`visibilitychange` → `visible`) JS เรียก `getQueueState()` แล้วเอาคำตอบมาทับ `_pos`, `_curItemIndex`, ไฮไลต์ย่อหน้า และตำแหน่งที่บันทึกไว้

แม้ JS จะหลับไปครึ่งชั่วโมงและพลาด `queueAdvance` ไปหลายร้อยครั้ง คำถามเดียวนี้ก็คืนตำแหน่งที่ถูกต้องได้ทันที

## 8. การจัดการข้อผิดพลาด

### 8.1 โหลดไฟล์ไม่สำเร็จ

native โหลดรายการถัดไปรอไว้ระหว่างที่รายการปัจจุบันกำลังเล่น (ปลั๊กอินทำอยู่แล้ว) ซึ่งเป็นบัฟเฟอร์กันเน็ตสะดุดสั้นๆ

1. ลองซ้ำ 3 ครั้ง เว้นระยะ 1 วินาที → 3 วินาที → 8 วินาที
2. ยังไม่สำเร็จ → หยุดคิว ไม่ข้ามย่อหน้า (การตัดสินใจของเจ้าของงาน: เนื้อหากฎหมายข้ามย่อหน้าเงียบๆ แย่กว่าหยุด)
3. หยุดแบบเห็นได้ — การ์ดบนล็อกสกรีนยังอยู่พร้อมชื่อมาตราที่ค้าง ในสถานะหยุด ไม่ใช่หายไป
4. ส่ง `queueStalled` — JS บันทึกลง `บันทึกปัญหาเสียง` เมื่อตื่นมา

### 8.2 audio focus

- ยึดชั่วคราว (แจ้งเตือน, นำทาง) → หยุดคิวไว้ แล้วเล่นต่อเองเมื่อได้ focus คืน
- ยึดถาวร (สายเข้า, แอปอื่นเล่นเพลง) → จบคิวอย่างสะอาด

ปัจจุบันเมื่อยึดถาวร ปลั๊กอินหยุดเล่นแต่ไม่แจ้ง JS ทำให้ลูปค้างรอตลอดกาล — บิลด์ 79 แก้แบบอ้อมฝั่ง JS ไว้แล้ว การย้ายคิวมา native ทำให้แก้ได้ตรงจุด

## 9. แคชและพื้นที่เก็บ

ไฟล์ที่ native โหลดตอนแบคกราวด์ลงแคชของ ExoPlayer (`cacheDir/media`, 100 MB, LRU) ซึ่ง `src/components/AudioStorageRow.jsx` มองไม่เห็น ทำให้ตัวเลขที่แสดงต่ำกว่าความจริง

**แก้:** เพิ่มคำสั่งอ่านขนาดแคชนั้นในปลั๊กอิน ให้ `AudioStorageRow` แสดงผลรวมของทั้งสองก้อน และปุ่มล้างล้างทั้งคู่ (`RemoteAudioAsset.clearCache()` มีอยู่แล้ว)

**ข้อจำกัดที่ยอมรับ:** การแยกขนาดตามเสียงชาย/หญิงครอบคลุมเฉพาะแคชของแอปเอง ก้อนของ ExoPlayer แยกตามเสียงไม่ได้ จะแสดงเป็นรายการรวมรายการเดียว

## 10. การทดสอบ

### 10.1 ฝั่ง JS (อัตโนมัติ)

เทสต์ใหม่สำหรับ `src/lib/nativeQueue.js`:

- สร้างรายการคิวถูกต้อง — เลือก `file://` เมื่อไฟล์อยู่ในแคชแอปแล้ว และ `https://` เมื่อยังไม่มี
- metadata ของแต่ละรายการตรงกับ `nowPlayingFor()` เดิม
- `itemIndex` / `paraIndex` ตรงกับ `_flat`
- โหมด repeat ถูกส่งตรงกับค่าใน `REPEAT_MODES`
- `getQueueState()` ที่คืนมาถูกนำไปทับ `_pos` และ `_curItemIndex` อย่างถูกต้อง รวมถึงกรณี `index: -1` (ไม่มีคิว) และกรณี `stalled: true`
- ฟังก์ชันเดิมชี้ไปคำสั่งที่ถูกต้องตามตาราง §6.4 — `pause`, `resume`, `next`, `prev`, `goToItem`, `stop`, `setRepeat`, `setRate`
- แพลตฟอร์มเว็บและ iOS ยังวิ่งลูปเดิม ไม่แตะคิว native
- สวิตช์ถอยใน §11 ปิดแล้วกลับไปวิ่งลูปเดิมบน Android ได้จริง

เทสต์เดิม 429 ตัวต้องผ่านทั้งหมด เพราะลูปเก่าไม่ถูกแก้

### 10.2 ฝั่ง native (ทดสอบบนเครื่องจริง)

ทดสอบอัตโนมัติไม่ได้ ใช้ขั้นตอนผ่าน `adb` ที่พิสูจน์แล้วในเซสชันนี้:

1. ต่อสาย USB เปิดแอป กดเล่น กด Home
2. poll `dumpsys audio | grep '/<pid> state:'` ทุก 3 วินาที
3. ผ่านเมื่อเห็นเครื่องเล่นสลับตัวใหม่ต่อเนื่อง **60 นาทีโดยไม่มีช่วงว่าง**
4. ตรวจ `บันทึกปัญหาเสียง` ใน Settings หลังจบ — heartbeat ทั้งสองควรหยุดตั้งแต่นาทีแรก ขณะที่เสียงเล่นครบชั่วโมง

## 11. สวิตช์ถอย

ค่าคงที่ใน `src/config.js` สำหรับปิดคิว native แล้วกลับไปใช้ลูป JS เดิม เพราะโค้ด native แก้แต่ละครั้งต้องรอ CI (บิลด์ในเครื่องใช้ไม่ได้จากปัญหาชื่อ SDK `android-36` กับ `android-36.1`) ถ้าเจอปัญหาบนเครื่องผู้ใช้จริงจะได้ถอยในบิลด์เดียว

---

## 12. สิ่งที่จงใจไม่ทำในรอบนี้

- **ให้ native จำตำแหน่งลงดิสก์เผื่อระบบฆ่าแอปทิ้ง** — เป็นปัญหาที่มีอยู่เดิม ไม่ได้เกิดจากงานนี้
- **ย้ายไป iOS** — ยังไม่ยืนยันว่ามีอาการเดียวกัน และไม่มีเครื่อง Mac ทดสอบ
- **ให้ native เรียก TTS ในเครื่องเมื่อไม่มีไฟล์** — ทุกมาตราในคอร์ปัสมีไฟล์ครบ 3,109/3,109 มาตรา 6,764 ย่อหน้า ไม่มีรูโหว่ เส้นทางนี้จึงใช้เฉพาะกรณีไฟล์เสีย ซึ่ง §8.1 ตัดสินให้หยุดแทน

## 13. ความเสี่ยงที่เหลือ

| ความเสี่ยง | ระดับ | การรับมือ |
|---|---|---|
| native เล่นได้เกิน 3 นาทีแต่ไม่ถึงชั่วโมง (วัดจริงมาแค่ ~3 นาที) | ต่ำ — ไม่มีสัญญาณเสื่อมใดๆ ในข้อมูล | เกณฑ์รับ §4 วัด 60 นาทีจริงก่อนปล่อย |
| โค้ดเครื่องเล่นสองชุดแยกกันดูแล | ปานกลาง | แยกโมดูลชัด ไม่แก้ลูปเดิม สวิตช์ถอยใน §11 |
| patch ปลั๊กอินใหญ่ขึ้น อัปเกรดยากขึ้น | ปานกลาง | สร้าง patch ใหม่ทุกครั้งและยืนยันด้วยการติดตั้งใหม่ตามขั้นตอนเดิม |
| ตัวเลขพื้นที่เก็บใน Settings เพี้ยนระหว่างทาง | ต่ำ | แก้พร้อมกันใน §9 ไม่ปล่อยทีหลัง |
