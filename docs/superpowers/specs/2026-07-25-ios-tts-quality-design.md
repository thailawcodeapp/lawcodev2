# แก้ปัญหาคุณภาพเสียงอ่าน iOS — Design

วันที่: 2026-07-25
สถานะ: รออนุมัติ
สาขา: `cloud-sync`

---

## 1. ปัญหา

หลังเปิดให้ผู้ใช้ทั่วไปใช้งานบน App Store ผู้ใช้ iOS รายงานว่าเสียงอ่าน "เหมือน AI รุ่นเก่า ไม่มีคุณภาพ" ทั้งที่ได้ดาวน์โหลดเสียง enhanced ของ Apple แล้ว ขณะที่ฝั่ง Android (Google TTS) เสียงปกติดี

เป้าหมายคือแก้ให้ **ยั่งยืน** และ **ไม่มีค่าใช้จ่ายรายเดือน**

## 2. สิ่งที่ตรวจพบ

### 2.1 Bug: resolver cache เสียงค้างถาวร

`src/lib/tts.js:89` เก็บผลการเลือกเสียงไว้ใน promise ระดับ module โดยไม่มีวันหมดอายุ

```js
let _iosVoicePromise = null;
function resolveIosBestVoice() {
  if (_iosVoicePromise) return _iosVoicePromise;   // cache ตลอดอายุ JS context
```

ลำดับเหตุการณ์ที่ทำให้เกิดอาการ:

1. ผู้ใช้เปิดแอป → resolver จำ index ของเสียง compact (เพราะยังไม่มี enhanced)
2. ผู้ใช้ออกไปที่ iOS Settings → ดาวน์โหลด Kanya (Enhanced)
3. กลับเข้าแอป — WebView ยังไม่ถูกทำลาย JS context เดิมยังอยู่
4. แอปยังใช้ index ของเสียง compact ต่อไป จนกว่าจะ force-quit

ตรงกับอาการที่ผู้ใช้รายงานทุกประการ

### 2.2 Bug: เก็บเสียงเป็น index ไม่ใช่ ID

ปลั๊กอิน `@capacitor-community/text-to-speech` รับพารามิเตอร์ `voice` เป็น **ลำดับ (Int)** ใน `AVSpeechSynthesisVoice.speechVoices()`

```swift
// TextToSpeech.swift:41
if voice >= 0 {
    let allVoices = AVSpeechSynthesisVoice.speechVoices()
    if voice < allVoices.count {
        utterance.voice = allVoices[voice]
```

ลำดับของ array นี้ **เลื่อนได้เมื่อผู้ใช้ติดตั้งหรือลบเสียง** แอปบันทึกค่านี้ลง `settings.ttsVoice` แบบถาวร → หลังผู้ใช้ลงเสียงเพิ่ม index เดิมอาจชี้ไปเสียงคนละตัวหรือคนละภาษา

`getSupportedVoices` คืน `voiceURI` = `voice.identifier` (เช่น `com.apple.voice.enhanced.th-TH.Kanya`) ซึ่งเสถียร ควรใช้ค่านี้แทน

### 2.3 Bug: อ่านเลขมาตราที่มี "/" ผิด

ผู้ใช้ทดสอบพบว่า `มาตรา 172/2` ถูกอ่านว่า "มาตรา **เศษ** 172 **ส่วน** 2" คำอ่านที่ถูกต้องตามที่นักกฎหมายใช้คือ "มาตรา 172 **ทับ** 2"

ขอบเขตผลกระทบ (วัดจากตัวบทจริง):

| จุด | จำนวน |
|---|---|
| เลขมาตราในหัวข้อ | 264 มาตรา (8.5% ของทั้งหมด) |
| อ้างอิงภายในตัวบท | 436 ครั้ง ใน 291 มาตรา |
| **รวม** | **~700 จุด** |

### 2.4 ปัญหาการเว้นวรรค

ตัวบทกฎหมายไทยใช้ **ช่องว่าง** เป็นตัวแบ่งวรรค แต่ TTS มองช่องว่างเป็นสิ่งที่ไม่มีความหมาย จึงอ่านรวดไม่หยุด

```
ผู้ใดจงใจหรือประมาทเลินเล่อ␣ทำต่อบุคคลอื่นโดยผิดกฎหมายให้เขาเสียหายถึงแก่ชีวิตก็ดี␣แก่ร่างกายก็ดี
```

สมมติฐาน: แปลงช่องว่างเป็นเครื่องหมายจุลภาคก่อนส่งเข้า TTS จะทำให้เว้นวรรคถูกต้อง — **ต้องทดสอบจริง ยังไม่ยืนยัน**

### 2.5 คำต่อท้ายไทยในเลขมาตรา

พบ 64 มาตรา: ทวิ (34), ตรี (15), จัตวา (6), เบญจ (4), **ฉ (3)**, สัตต (1), อัฏฐ (1)

ตัว "ฉ" ตัวเดียวโดด ๆ ต้องอ่านว่า "ฉอ" ซึ่ง TTS น่าจะอ่านผิด — ต้องตรวจสอบในการทดสอบ

### 2.6 ขนาดคลังข้อมูล

| ประมวล | มาตรา | ย่อหน้า | อักษร | ความยาวเสียง | ขนาด (Opus 24k) |
|---|---|---|---|---|---|
| แพ่งและพาณิชย์ | 1,870 | 3,412 | 533,923 | 19.8 ชม. | 213 MB |
| วิ.แพ่ง | 468 | 1,462 | 322,114 | 11.9 ชม. | 129 MB |
| อาญา | 448 | 937 | 161,367 | 6.0 ชม. | 65 MB |
| วิ.อาญา | 323 | 959 | 153,663 | 5.7 ชม. | 61 MB |
| **รวม** | **3,109** | **6,770** | **1,171,067** | **43.4 ชม.** | **468 MB** |

หน่วยการแบ่ง: 6,770 ย่อหน้า (เฉลี่ย 2.2/มาตรา) เทียบกับ 13,409 chunk แบบปัจจุบัน (เฉลี่ย 4.3/มาตรา)
37% ของย่อหน้ายาวเกิน 180 ตัวอักษรจนถูก `splitLong()` ซอยกลางคัน

## 3. เป้าหมาย และสิ่งที่ไม่ทำ

### เป้าหมาย

1. เสียงอ่าน iOS ต้องฟังเป็นธรรมชาติในระดับที่ผู้ใช้ยอมรับได้
2. ไม่มีค่าใช้จ่ายรายเดือนที่ผูกพัน
3. อ่านเลขมาตราและเว้นวรรคถูกต้อง
4. ทำงานได้แม้ไม่มีอินเทอร์เน็ต (ไม่มีทางตัน)
5. ไม่กระทบ Android ที่ทำงานดีอยู่แล้ว

### สิ่งที่ไม่ทำ (Non-goals)

- ไม่ทำเสียงอ่านภาษาอังกฤษ (ตัวบท eng) ในรอบนี้
- ไม่ทำ Sign in with Apple / ลบบัญชีในแอป (คนละเรื่อง)
- ไม่เปลี่ยนระบบโควตา (คงเดิม 5/วัน +3 ต่อโฆษณา)
- ไม่ทำเสียงอ่านสำหรับ TOC / ชื่อหมวด — เฉพาะตัวบทมาตรา

### สิ่งที่ตัดสินใจแล้ว

- เสียงคุณภาพสูง **ให้ทุกคนฟังฟรี** ภายใต้โควตาเดิม 5 มาตรา/วัน (ไม่ Pro-gate)

## 4. สถาปัตยกรรมรวม — 3 เฟส

```
เฟส 1  Text normalization + แก้ bug เลือกเสียง     → ปล่อยได้ทันที ฟรี ได้ทั้ง 2 แพลตฟอร์ม
เฟส 2  Pilot สร้างเสียงจริง 10 มาตรา เทียบเสียง      → ตัดสินใจด้วยหู + รู้ราคาจริง
เฟส 3  Pipeline render ทั้งหมด → R2 → เปลี่ยนตัวเล่น  → เสียง neural ทั้งแอป
```

เหตุผลที่เรียงลำดับนี้:

- เฟส 1 เป็น **prerequisite ของเฟส 3** — ต้องแปลง `172/2` → `172 ทับ 2` ก่อนส่งเข้า Google อยู่ดี ไม่งั้นไฟล์เสียง 264 มาตราจะผิดถาวรและต้อง render ใหม่ (เสียเงินซ้ำ)
- เฟส 1 ยังเป็น **fallback ถาวร** ของเฟส 3 เมื่อออฟไลน์หรือไฟล์ยังไม่โหลด
- เฟส 1 ปล่อยได้เลย ผู้ใช้ที่เดือดร้อนตอนนี้ได้ประโยชน์ก่อน

เฟส 1 และ 2 ทำคู่ขนานกันได้

### ขอบเขตของแผนลงมือครั้งแรก

เอกสารนี้ครอบคลุมทั้ง 3 เฟสเพื่อให้เห็นปลายทาง แต่ **แผนลงมือ (implementation plan) ฉบับแรกจะครอบคลุมเฉพาะเฟส 1 และ 2 เท่านั้น**

เฟส 3 จะเขียนแผนแยกต่างหากหลังจากที่:
- ~~ตรวจเงื่อนไขการใช้งานของ Google~~ ✅ ผ่านแล้ว
- ~~พิสูจน์ว่าเล่นไฟล์เสียงตอนปิดจอได้~~ ✅ ผ่านแล้ว (เฟส 0, ดู §7.9)
- เฟส 2 ให้คำตอบเรื่อง engine, เสียง, และราคาจริง ← **เหลือข้อนี้ข้อเดียว**

### เฟส 0 — de-risk (ทำไปแล้ว)

ก่อนลงทุนเขียนอะไร ปิดความเสี่ยงสองข้อที่ทำให้เฟส 3 ทั้งเฟสไม่มีความหมายถ้าไม่ผ่าน
ใช้ branch `spike/background-audio` ซึ่งแยกจาก `cloud-sync` ทั้งหมด ผลอยู่ใน §7.9 และ §9

บทเรียนของวิธีทำงาน: การทดสอบ 3 รอบใช้เวลาไม่ถึงวัน แต่เปลี่ยนคำตอบสองครั้ง
(HTML5 ใช้ได้ → HTML5 ใช้ไม่ได้ → ต้องใช้ native plugin) ถ้าข้ามขั้นนี้ไปเรนเดอร์ 6,770 ไฟล์ก่อน
จะได้สถาปัตยกรรมที่พังในมือผู้ใช้จริงโดยไม่มีใครรู้จนสาย

## 5. เฟส 1 — Text normalization + แก้ bug เลือกเสียง

### 5.1 โมดูลใหม่: `src/lib/thaiSpeech.js`

โมดูลบริสุทธิ์ (pure) ไม่มี dependency ทดสอบได้ง่าย ใช้ร่วมกันทั้งฝั่งแอปและฝั่ง pipeline เรนเดอร์เสียง

```js
export function normalizeForSpeech(text) -> string
```

กฎการแปลง (เรียงตามลำดับที่ใช้):

| # | กฎ | ตัวอย่าง |
|---|---|---|
| 1 | `\d+/\d+` → `$1 ทับ $2` | `193/30` → `193 ทับ 30` |
| 2 | `ฉ` ที่ยืนเดี่ยวถัดจากเลขมาตรา → `ฉอ` (ต้องไม่โดน `ฉ` ที่เป็นส่วนของคำอื่น จึงบังคับให้ขนาบด้วยขอบเขตคำทั้งสองด้าน และต้องมีเลขมาตรานำหน้า) | `มาตรา 281 ฉ` → `มาตรา 281 ฉอ` |
| 3 | ช่องว่างระหว่างวรรค → `, ` | `...ก็ดี แก่ร่างกาย...` → `...ก็ดี, แก่ร่างกาย...` |
| 4 | ยุบช่องว่าง/จุลภาคซ้ำ | `, ,` → `,` |

**ข้อควรระวังของกฎที่ 3:** ต้องไม่แทรกจุลภาคภายในตัวเลขหรือระหว่างตัวเลขกับหน่วย และต้องทดสอบว่า Apple TTS ไม่หยุดนานเกินไปจนฟังกระตุก หากผลลัพธ์แย่ ให้ถอยกฎนี้ออกโดยไม่กระทบกฎอื่น (ออกแบบให้เปิด/ปิดแยกได้)

**ความเสี่ยงของกฎที่ 1:** ต้องไม่ไปโดนเศษส่วนจริงในตัวบท (เช่น อัตราดอกเบี้ย) — ต้องตรวจตัวอย่างที่แมตช์ทั้ง 700 จุดก่อนปล่อย

### 5.2 จุดที่เรียกใช้

`src/lib/tts.js` → `buildSectionItem()` เรียก `normalizeForSpeech()` กับ:
- ข้อความหัวมาตรา `มาตรา ${number}`
- ทุกย่อหน้าก่อนเข้า `splitLong()`

**สำคัญ:** normalize เฉพาะข้อความที่ส่งเข้า TTS เท่านั้น ข้อความที่แสดงบนหน้าจอและที่ใช้ค้นหา **ต้องไม่ถูกแตะ**

### 5.3 แก้ bug resolver cache (2.1)

- ลบ cache แบบถาวร เปลี่ยนเป็น cache ที่ล้างได้
- เพิ่ม listener `App.addListener('resume', ...)` จาก `@capacitor/app` เพื่อล้าง cache ทุกครั้งที่กลับเข้าแอป — ครอบคลุมกรณีผู้ใช้ออกไปโหลดเสียงแล้วกลับมา
- ปุ่ม "ทดสอบฟังเสียง" ในหน้าตั้งค่าให้ล้าง cache ก่อนเสมอ

### 5.4 แก้ bug voice index (2.2)

- เปลี่ยน `settings.ttsVoice` จากเก็บ index เป็นเก็บ `voiceURI`
- ตอนจะพูด: แปลง `voiceURI` → index ปัจจุบัน โดยค้นใน `getSupportedVoices()` ครั้งนั้น ๆ
- ถ้าหา `voiceURI` ไม่เจอ (ผู้ใช้ลบเสียงไปแล้ว) → ถอยไปใช้ auto-best
- **Migration:** ค่าเดิมที่เป็นตัวเลขล้วนถือเป็น legacy → ล้างทิ้ง ตั้งเป็น auto เพราะไม่มีทางแปลงย้อนกลับได้อย่างถูกต้อง

### 5.5 ผลที่คาดหวังของเฟส 1

- 700 จุดที่อ่าน "เศษ...ส่วน..." อ่านถูกเป็น "ทับ"
- เสียง enhanced ถูกใช้จริงทันทีหลังผู้ใช้ดาวน์โหลด ไม่ต้อง force-quit
- เว้นวรรคดีขึ้น (รอยืนยันจากการทดสอบ)
- **ได้ประโยชน์ทั้ง iOS และ Android**

## 6. เฟส 2 — Pilot

### 6.1 วัตถุประสงค์

ตัดสินใจเลือก engine และเสียงด้วยการฟังจริง พร้อมวัดราคาจริงจากบิล ก่อนลงทุนสร้าง pipeline เต็ม

### 6.2 ขอบเขต

สคริปต์ใช้ครั้งเดียวใน `scripts/tts-pilot/` (ไม่รวมในแอป) สร้างไฟล์เสียงจากมาตราจริง 10 มาตรา คัดให้ครอบคลุม:

- มาตราสั้น (< 150 ตัวอักษร)
- มาตรายาว (> 800 ตัวอักษร)
- มาตราที่มีเลข `/` เช่น 193/30
- มาตราที่มีคำต่อท้ายไทย (ทวิ, ฉ)
- มาตราหลายย่อหน้า

### 6.3 ตัวแปรที่เทียบ

| ตัวแปร | ค่าที่ทดสอบ |
|---|---|
| Engine | Chirp 3: HD, Gemini-TTS |
| เสียง (Chirp3) | Gacrux (ญ, Mature), Charon (ช, Informative), Schedar (ช, Even), Erinome (ญ, Clear) |
| Normalization | เปิด vs ปิด |
| หน่วยเรนเดอร์ | ทั้งย่อหน้า vs ซอย 180 ตัวอักษร (เพื่อยืนยันว่าย่อหน้าให้น้ำเสียงดีกว่าจริง) |

### 6.4 เกณฑ์ตัดสิน

1. ความเป็นธรรมชาติของน้ำเสียง เทียบกับ Apple enhanced
2. ความถูกต้องของการเว้นวรรค
3. การอ่านศัพท์กฎหมาย (ทวิ, ฉ้อฉล, นิติกรรมอำพราง, เลขมาตรา)
4. ความล้าเมื่อฟังต่อเนื่อง (ฟังไฟล์ยาวสุดจนจบ)
5. ราคาจริงต่อ 1 ล้านตัวอักษร จากบิล

### 6.5 ผลลัพธ์ที่ต้องได้

- เลือก engine + เสียง 1 ตัว
- ตัวเลขราคาจริงสำหรับ 1.17 ล้านตัวอักษร
- ยืนยันหรือปฏิเสธสมมติฐานเรื่องช่องว่าง → จุลภาค

## 7. เฟส 3 — Pre-rendered audio

### 7.1 หน่วยการแบ่ง: ย่อหน้า

**ตัดสินใจ: 1 ย่อหน้า = 1 ไฟล์เสียง** (6,770 ไฟล์ ~70 KB/ไฟล์ เฉลี่ย 23 วินาที)

เหตุผลที่ไม่ใช้ chunk (13,409 ไฟล์):

- `splitLong(180)` มีไว้แก้ข้อจำกัดของ TTS เท่านั้น ไฟล์เสียงไม่มีข้อจำกัดนี้
- ถ้าเรนเดอร์ทีละ chunk เครื่องสังเคราะห์จะมองแต่ละ chunk เป็นประโยคเดี่ยว → ลงเสียงท้าย chunk เหมือนจบประโยคทั้งที่ยังไม่จบ และได้ยินรอยต่อกลางวรรค
- ย่อหน้าตรง 1:1 กับ `paraIndex` → ไฮไลต์ย่อหน้าใน `ReaderScreen.jsx:72` ทำงานเหมือนเดิม ไม่ต้องสร้าง timing metadata
- ไม่ผูกไฟล์เสียงกับค่าคงที่ 180 ที่อาจเปลี่ยนภายหลัง

เหตุผลที่ไม่ใช้ทั้งมาตรา: ไฮไลต์ย่อหน้าจะพัง ต้องทำ SSML timepoints เพิ่มอีกชั้น

### 7.2 การตั้งชื่อไฟล์: content-addressed

ชื่อไฟล์ = hash ของ **ข้อความย่อหน้าหลัง normalize** เช่น `a3f9c2d1....opus`

| เหตุการณ์ | ผลลัพธ์ |
|---|---|
| แก้ตัวบทมาตราใด | hash เปลี่ยน → ไม่มีไฟล์ → **ถอยไป TTS อัตโนมัติ ไม่พัง** แล้วค่อย render เฉพาะย่อหน้านั้น |
| ย่อหน้าซ้ำหลายมาตรา | ใช้ไฟล์เดียวกัน ประหยัดพื้นที่ |
| CDN | URL ไม่มีวันเปลี่ยน → cache ถาวร (immutable) |
| เปลี่ยนกฎ normalize | hash เปลี่ยนทั้งชุด → ต้อง render ใหม่ (จึงต้องล็อกกฎให้นิ่งในเฟส 2 ก่อน) |

### 7.3 Manifest

ไฟล์ JSON แมป `sectionId` → รายการ hash เรียงตามย่อหน้า

**ตัดสินใจ: รวม manifest ไปกับตัวแอป** (ไม่ดาวน์โหลด)
- ขนาดรวมประมาณ 300 KB ทั้ง 4 ประมวล — เล็กพอ
- ผลคือแอปรู้ URL ของทุกย่อหน้าตั้งแต่ติดตั้ง ไม่ต้องต่อเน็ตเพื่อถาม
- manifest เปลี่ยนเมื่อ render ใหม่เท่านั้น ซึ่งไปพร้อมกับการอัปเดตแอปอยู่แล้ว

### 7.4 Pipeline (รันในเครื่อง ไม่ใช่ใน CI)

`scripts/tts-render/`

```
อ่าน public/data/*-th.json
  → แยกย่อหน้า
  → normalizeForSpeech()          [ใช้โมดูลเดียวกับแอป]
  → hash
  → ถ้ามีไฟล์อยู่แล้ว ข้าม        [resumable กลับมารันต่อได้]
  → เรียก Google TTS API          [1 ย่อหน้า = 1 request]
  → เข้ารหัส Opus/AAC
  → อัปโหลดขึ้น R2
  → เขียน manifest
```

#### ทำไม 1 ย่อหน้า = 1 request

ลิมิตของ Google คือ **5,000 ไบต์ต่อ request เท่ากันทุกโมเดล** (รวม Chirp 3 HD และ Gemini-TTS)
ภาษาไทยกิน 3 ไบต์ต่อตัวอักษร วัดกับตัวบทจริงได้:

| | ไบต์ | ผล |
|---|---|---|
| ย่อหน้ายาวสุด | 3,998 | ✅ พอดี เหลือที่ว่าง 20% |
| ย่อหน้าที่เกินลิมิต | **0 จาก 6,770** | ✅ ไม่ต้องซอยย่อหน้าเลย |
| ถ้าส่งทั้งมาตรา | สูงสุด 14,097 | ❌ **40 มาตรา (1.3%) เกินลิมิต** |

จึงไม่ใช่แค่ "แบ่งตามย่อหน้าเพราะอยากได้ไฟล์แยกไว้ไฮไลต์" แต่การส่งทั้งมาตราทำไม่ได้จริงอยู่แล้ว

#### เวลาและต้นทุน

Chirp 3 จำกัด **200 requests/นาที** → 6,697 ย่อหน้าไม่ซ้ำ ≈ **34 นาที** ต้องหน่วงคำขอไว้ที่ ~180/นาที
และถอยเพิ่มเป็นทวีคูณเมื่อเจอ 429

1.16M อักษร กับโควตาฟรี 1M อักษร/เดือน → **฿0 ถ้าแบ่งเรนเดอร์ 2 เดือน** หรือ ~$5 ถ้ารันรวดเดียว

การ dedup ด้วย hash ประหยัดได้แค่ 73 ไฟล์ (0.3%) — คุณค่าจริงของ hash คือ resume ได้และ
ถอยไป TTS อัตโนมัติเมื่อไฟล์ไม่ตรง ไม่ใช่การประหยัดเงิน

#### ด่านตรวจก่อนประกาศว่าเสร็จ

ความเสี่ยงที่แท้จริงไม่ใช่ request ที่ error (เห็นชัดอยู่แล้ว) แต่คือ **request ที่คืน 200 พร้อมเสียงที่ผิด**
ฟังเองครบ 6,770 ไฟล์ไม่ไหว จึงต้องมีด่านอัตโนมัติ:

| ตรวจ | จับอะไร |
|---|---|
| **ความยาวเสียงจริง เทียบกับที่คาดจากจำนวนอักษร (±40%)** | **ข้อความถูกตัดกลางคัน — สำคัญที่สุด** |
| amplitude สูงสุดไม่ใช่ศูนย์ | ไฟล์เงียบ/ว่างเปล่า |
| ไฟล์มีจริงบน R2 และขนาดตรงกับที่อัป | อัปโหลดหลุด |
| ทุก hash ใน manifest มีไฟล์คู่กัน | เรนเดอร์ไม่ครบ |

จากนั้นสุ่มฟังด้วยหู: ทุกไฟล์ที่ตกด่านข้างบน + สุ่ม 30 ไฟล์ + เจาะ 20 มาตราที่มีเลข `/`

**ล็อกกฎ normalize ให้นิ่งก่อนเรนเดอร์** — ชื่อไฟล์คือ hash ของข้อความหลัง normalize
แก้กฎทีหลังเท่ากับ hash เปลี่ยนทั้งชุดและต้องเรนเดอร์ใหม่ทั้งหมด

รองรับผู้ใช้ระดับ 10,000 คน/วัน ได้โดยยังอยู่ใน free tier → **฿0/เดือน**

ทางเลือกสำรองที่พิจารณาแล้วไม่เลือก:
- **GitHub Releases** — ฟรีแต่ ToS ไม่ได้ออกแบบมาให้เป็น CDN ของแอป เสี่ยงถูกจำกัด
- **Firebase Storage** — มีอยู่แล้วในโปรเจกต์ แต่ free tier ดาวน์โหลดจำกัด 1 GB/วัน จะเกินเมื่อผู้ใช้โต แล้วกลายเป็นค่ารายเดือน ผิดเป้าหมาย
- **jsDelivr** — จำกัดขนาดไฟล์และไม่เหมาะกับ 468 MB

### 7.6 ฝั่งแอป

โมดูลใหม่:

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/audioManifest.js` | โหลด manifest, แมป sectionId+paraIndex → hash |
| `src/lib/audioCache.js` | เก็บ/อ่านไฟล์เสียงในเครื่องผ่าน Capacitor Filesystem, ลบแคช, รายงานขนาด |
| `src/lib/audioPlayer.js` | เล่นไฟล์เสียง 1 ไฟล์ คืน promise แบบเดียวกับ `speakOne()` — native ใช้ปลั๊กอิน, เว็บใช้ HTML5 |

แก้ `src/lib/tts.js`:
- `buildSectionItem()` — ถ้ามี manifest ให้สร้าง unit ระดับย่อหน้าพร้อม `audioHash` ถ้าไม่มีให้ซอย 180 แบบเดิม
- `speakOne(unit)` — ถ้ามี `audioHash` และเล่นได้ → `audioPlayer.play()` ไม่งั้น → TTS เดิม

**loop หลัก, pause/resume, next/prev, playlist, โควตา, สถิติ ไม่ต้องแก้** เพราะยังเป็นสัญญาเดิม: "เล่นหน่วยนี้จนจบแล้ว resolve"

**ข้อควรระวังที่เกิดใหม่จากการเลือกปลั๊กอิน:** ตอนถอยไป TTS กลางเพลย์ลิสต์ จะมีสองระบบที่ตั้งค่า
audio session คนละที่ (`@capgo/native-audio` กับ `@capacitor-community/text-to-speech`)
ต้องออกแบบให้สลับกันโดยไม่แย่ง session และต้องทดสอบเคสนี้โดยเฉพาะ

### 7.7 ลำดับการเล่นและ fallback

```
ต้องการเล่นย่อหน้า
  ├─ มีไฟล์ในเครื่อง?        → เล่นจากเครื่อง         [ออฟไลน์ได้]
  ├─ มีเน็ต?                → ดาวน์โหลด → เก็บ → เล่น
  └─ ไม่มีทั้งคู่            → TTS ในเครื่อง          [ไม่มีทางตัน]
```

โหลดล่วงหน้า: ขณะเล่นย่อหน้าปัจจุบัน ดาวน์โหลดย่อหน้าถัดไปไว้ก่อน เพื่อไม่ให้สะดุดระหว่างย่อหน้า

### 7.8 การดาวน์โหลดล่วงหน้าทั้งเล่ม

หน้าตั้งค่าเพิ่มส่วน "เสียงออฟไลน์":
- แสดงแต่ละประมวลพร้อมขนาด (แพ่ง 213 MB, วิ.แพ่ง 129 MB, อาญา 65 MB, วิ.อาญา 61 MB)
- ปุ่มโหลด/ยกเลิก พร้อมแถบความคืบหน้า
- ปุ่มลบแคชรายเล่ม และแสดงพื้นที่ที่ใช้ไปทั้งหมด

### 7.9 ประเด็นเทคนิคที่ต้องแก้

**เล่นเสียงตอนปิดจอ — ทดสอบบนเครื่องจริง 3 รอบ สรุปแล้ว ✅**

ทดสอบบน branch `spike/background-audio` (iOS build 1.0.4 (18)–(20)) ไฟล์เสียงพูดบอกหมายเลขตัวเอง
เพื่อให้ตัดสินด้วยหูตอนจอล็อกได้

| รอบ | ทดสอบ | ผล |
|---|---|---|
| 1 | เล่นต่อกัน 3 ไฟล์ ไม่มีช่วงเงียบ (HTML5 และ native plugin) | ✅ ทั้งคู่ผ่าน · ปุ่มบนหน้าล็อกขึ้นเอง |
| 2 | เว้นช่องว่าง 3 วินาที (จำลองรอโหลด) | ❌ **พัง** — `play()` ผ่าน `onplaying` ยิง แต่ `currentTime` ค้าง 0.0 |
| 3 | สี่วิธีกัน session ขาด ที่ช่องว่าง 3 วินาทีเท่ากัน | A ใหม่ทุกครั้ง ❌ · B element เดิมสลับ src ❌ · **C เสียงเงียบคลอ ✅ · D native plugin ✅** |

**กลไกที่แท้จริง:** ตัวที่ตายไม่ใช่การสร้าง element ใหม่ (รอบ 3 วิธี B ใช้ element เดิมก็ยังพัง)
และไม่ใช่แอปถูก suspend (timer ยิงตรงเวลาเสมอ) แต่เป็น **audio session ถูก iOS ปิดเมื่อไม่มีเสียงเล่น
แล้วแอปที่อยู่เบื้องหลังไม่มีสิทธิ์เปิดใหม่** — งบช่องว่างที่ยอมรับได้จึงเท่ากับ **0 วินาที**

**ตัดสินใจ: ใช้ `@capgo/native-audio` (วิธี D)**

C กับ D ผ่านเหมือนกัน แต่เลือก D เพราะ:

1. **ทนการขัดจังหวะในชีวิตจริง** — C มีจุดตายเดียวคือถ้าเสียงเงียบหยุด ทุกอย่างตายตาม และสิ่งที่ทำให้
   หยุดได้คือเหตุการณ์ที่เกิดทุกวัน เช่นสายโทรเข้าระหว่างปิดจอฟัง พอวางสายเสียงเงียบไม่กลับมาเอง
   → session ว่าง → เสียงตายถาวรจนกว่าจะปลดล็อกมากด ส่วน D ให้ AVFoundation จัดการ interruption/resume
   ซึ่งเป็นงานที่มันออกแบบมาเพื่อการนี้
2. **ตรงกับวิธีที่แอปเสียงจริงใช้** — Spotify และแอปพอดแคสต์เปิด `AVAudioSession` หมวด `.playback`
   ครั้งเดียวแล้วไม่ปิดเลย และเปลี่ยนแทร็กภายใน `AVQueuePlayer` เครื่องเสียงจึงไม่เคยหยุด
   ไม่ต้องกลับมาขอสิทธิ์ใหม่ — D คือแนวเดียวกัน ส่วน C คือการเลียนแบบผลลัพธ์ด้วยวิธีอ้อม
3. **ไม่พึ่งพฤติกรรมที่ไม่มีเอกสารรับรอง** — C ต้องตั้ง `volume` เป็น 0.01 ไม่ใช่ 0 เพราะเดาว่า iOS
   อาจถือว่าเงียบสนิทเท่ากับไม่มีเสียง ถ้า iOS รุ่นหน้ามองทะลุก็พังทันที

ราคาที่ยอมจ่าย: เพิ่ม native dependency และต้องจัดการ session ไม่ให้ชนกับปลั๊กอิน TTS (ดู §7.6)

**ยังไม่ได้ทดสอบ:** เล่นยาวหลายสิบนาที (รอบที่ยาวสุดคือ ~40 วินาที) — ต้องปิดก่อนเรนเดอร์ทั้งหมด

**ควบคุมความเร็ว** — ปลั๊กอินมี `setRate()` ต้องยืนยันว่ารักษาระดับเสียงไม่ให้แหลมตอนเร่ง

**ปุ่มควบคุมบนหน้าล็อก** — ยืนยันแล้วว่าขึ้นให้เอง ผ่าน `showNotification: true` ของปลั๊กอิน

**สำรองข้อมูล iCloud** — ไฟล์เสียงต้องตั้ง `NSURLIsExcludedFromBackupKey` ไม่งั้นกิน iCloud ของผู้ใช้หลายร้อยเมกะไบต์ และอาจถูก Apple ปฏิเสธตอนรีวิว เก็บใน Directory.Data (ไม่ใช่ Cache ซึ่ง iOS ลบทิ้งได้เอง)

## 11. สรุปการตัดสินใจ

| หัวข้อ | ตัดสินใจ | เหตุผล |
|---|---|---|
| ลำดับงาน | เฟส 1 → 2 → 3 (1 กับ 2 คู่ขนาน) | เฟส 1 เป็น prerequisite และ fallback ของเฟส 3 |
| หน่วยเสียง | ย่อหน้า | น้ำเสียงต่อเนื่อง + ไฮไลต์ทำงานเดิม + ไม่ผูกกับค่า 180 |
| ชื่อไฟล์ | hash ของข้อความ | ทนต่อการแก้ตัวบท, fallback อัตโนมัติ, cache ถาวร |
| Manifest | รวมไปกับแอป | เล็ก (300 KB) และไม่ต้องต่อเน็ตเพื่อถาม |
| Hosting | Cloudflare R2 | egress ฟรีไม่จำกัด = ไม่มีค่ารายเดือนจริง |
| สิทธิ์การเข้าถึง | ฟรีทุกคน ภายใต้โควตาเดิม | ตามที่เจ้าของตัดสินใจ |
| Fallback | TTS ในเครื่องเสมอ | ไม่มีทางตัน แม้ออฟไลน์หรือไฟล์หาย |
| **ตัวเล่นเสียง** | **`@capgo/native-audio`** | HTML5 ตายเมื่อ session ขาด แม้เงียบแค่ 3 วินาที native จัดการ interruption (สายเข้า/Siri) ได้ และเป็นแนวเดียวกับที่แอปพอดแคสต์ใช้ |
| หน่วยส่งเข้า TTS | 1 ย่อหน้า = 1 request | ลิมิต 5,000 ไบต์ ทำให้ส่งทั้งมาตราไม่ได้ใน 40 มาตรา ส่วนย่อหน้าไม่เกินลิมิตเลยสักอัน |
